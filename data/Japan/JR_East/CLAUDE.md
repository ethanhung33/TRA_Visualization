# CLAUDE.md — 東日本旅客鉄道 (JR East)

## 基本資訊

- **calendar_type**: `WEEKDAY_BITMAP`
- **data_fetch_strategy**: `WEEKEND_FILE`（`timetable_weekday.json` / `timetable_holiday.json` 兩檔）
- **view_type**: 全為 `LINEAR`，山手線為 `CIRCULAR`
- **timezone_offset**: 9
- **規模**：79 條路線來源（含 4 條手動連絡段）→ 100 個 segment、1,646 個車站、73 個 view preset；平日 12,595 班 / 假日 11,832 班

新幹線（東北・北海道・上越・北陸・山形・秋田）**不在本系統**，已由
`data/Japan/Tohoku_Hokkaido_Joetsu_Hokuriku_Shinkansen/` 收錄；轉換階段以
`SKIP_TYPES = {"新幹線"}` 排除。

## 資料源

**官方時刻表站** `https://www.jreast-timetable.jp/`（列車詳情頁在 `timetables.jreast.co.jp`）。

比 navitime（其他日本線的預設來源）好的地方：有**真正的列車番号與列車種別**、
有「直通」標記、且是官方資料無商業服務的限速顧慮。實測 19,472 頁 0 失敗。

端點鏈：

| 階段 | 端點 | 取得 |
|------|------|------|
| 路線→車站 | `/cgi-bin/st_search.cgi?rosen={id}` | 該線各站的 `list{ID}.html`（rosen id 見 `timetable.py::ROSEN`） |
| 車站→方向 | `/timetable/list{ID}.html` | 每個「路線・方面」列有 平日 / 土曜・休日 連結（`a.fortimeLink` **前 2 個**；後面的「デジタル時刻表」不取） |
| 方向→列車 | `/{YYMM}/timetable/tt{ID}/{...}.html` | 該站該方向所有班次的 `/train/` 連結（**含普通車**） |
| 列車詳情 | `/{YYMM}/train/{...}.html` | 矩陣式表格：列車種別 / 列車名 / 列車番号 / 運転日 + 各站 着/発 |

## 執行流程

```
py data/Japan/JR_East/script/build_topology.py      # 維基 → topology.json
py data/Japan/JR_East/script/timetable.py           # 官方站 → raw_timetable.json（約 13 分）
py data/Japan/JR_East/script/convert_timetable.py   # raw → timetable_weekday/holiday.json
py data/Japan/JR_East/script/build_setting.py       # 讀時刻表 → setting.json（顏色/preset）
py tools/validate_system.py data/Japan/JR_East --timetable-sample 0
```

`timetable.py` 可用 `--lines 66,24` 只跑指定 rosen id、`--workers N` 調併發。
注意：掃某條線時會連帶抓到其車站頁上**所有**路線的方向頁（車站頁是跨線共用的），
故單跑一條幹線也會拉回大量鄰線班次。

## 特殊邏輯

### 拓樸用「法定路線」而非「營運系統名」

官方時刻表的路線是**營運系統名**（宇都宮線・京浜東北線・埼京線・湘南新宿ライン…），
彼此大量重疊（宇都宮線 ⊂ 東北本線、京浜東北線 ⊂ 東北本線＋東海道本線）。
segment 必須互不重疊，否則派段時同一班車會被複製到多個 segment。

因此 **topology = 法定路線**（互不重疊地分割路網），營運系統名只出現在
`setting.json` 的 `view_presets`，用 `{id, start, end}` 截取拼接還原（例：
京浜東北線 = 東北本線[大宮→東京] + 東海道本線[東京→横浜] + 根岸線）。

### 並行複線的車站聯集 (`MERGE_SOURCES`)

東京圈幹線是「電車線＋列車線」雙複線：各駅停車（京浜東北線・中央総武緩行線）與
快速/中距離電車停靠**不同的站集合**，維基寫在不同條目。只取一邊，另一邊的專屬站
（大井町・王子・飯田橋…）就不在拓樸裡，那些列車的停靠會整批掉光。

解法：同一 segment 取兩邊**聯集**依里程排序；快速車自然只停子集，在運行圖上畫成
斜率較大、跳過中間站的線——正是真實運行圖的樣子。額外來源的里程原點常不同
（京浜東北表是「大宮から」、主表是「東京から」），故以兩表共用站做**兩點線性對位**
換算。

> **聯集只能用在同一路廊的並行線**。品鶴線（横須賀線・湘南新宿ライン 的 西大井・武蔵小杉・
> 新川崎）與東海道本線（川崎經由）是實體分離的路線，早期把横須賀線表 東京–大船 整段聯集進
> `tokaido_main_line`，結果這三站出現在京浜東北線・東海道線視圖裡。現在：
> - `tokaido_main_line` 只聯集横須賀線的 **横浜–大船**（保土ケ谷・東戸塚，同一路廊）。
> - `hinkaku_line`（品川–西大井–武蔵小杉–新川崎–横浜）獨立成段。法定終點是鶴見，但
>   横須賀線在鶴見無月台、之後以自己的線路並行到横浜，故以 横浜 為交會站。
> - 横須賀線 preset = 東海道[東京→品川] + 品鶴線[品川→横浜] + 東海道[横浜→大船] + 横須賀線。

### 維基車站表解析（`wikitable.py`）

本機 Windows 應用程式控制原則封鎖 numpy/pandas 的原生 `.pyd`
（`ImportError: DLL load failed ... 應用程式控制原則已封鎖此檔案`），
無法用 `pandas.read_html`。改以純 BeautifulSoup 把表格展開成矩形 grid
（正確處理 `rowspan`/`colspan`）並攤平多層表頭——維基車站表大量使用 rowspan
（所在地、路線名跨多列），直接用 `tr.find_all('td')` 的索引取值會整列錯位。

其他必要處理：
- **跨條目的幹線區間**：東北本線 東京–黒磯 的車站表在「宇都宮線」條目、
  奥羽本線 福島–新庄 在「山形線」、中央本線 東京–高尾 在「中央線快速」、
  総武本線 東京–千葉 在「横須賀・総武快速線」＋「中央・総武緩行線」。
- **`TRIM_RANGE`**：來源表含多餘區間時裁到指定起訖站。
- **`PREPEND_STATION`**：來源表缺起點交會站時補回（鍵為**最終 segment id**）。
  例：大川支線法定為 武蔵白石–大川，但列車實際自 **安善** 分歧（不停武蔵白石），
  不補 安善 就沒有任何一班車能同時落在本段與鶴見線本線 → 整段空白。
- **`split_monotonic`**：里程不單調處切段（信越本線 高崎–横川 / 篠ノ井–長野 /
  直江津–新潟 在維基是分開的表，各自從 0 起算）。
- **不跨表去重**：分岔/支線的交會站（成田線我孫子支線的「成田」）本來就該同時出現
  在兩個 segment，前端正是靠共用站 id 偵測分岔。只在表格內部去重。

### 環狀線閉合 (`CLOSE_LOOP`)

前端的 `CIRCULAR` 用 `loopKm = 各 segment 里程跨距總和` 決定一圈高度並在該處回繞
（`main.js::buildLookupY`）。台鐵環島正確的原因是它的 segment 鏈**最後回到起站**
（`eastern_trunk` 結尾的八堵＝`north_main` 開頭的八堵），跨距總和恰為一圈全長。

但維基的山手線駅一覧只到 有楽町（累計 33.7），起站 東京 的「駅間」欄是 `-`，
**沒有收尾的 有楽町→東京 一段**。照抄會讓 `loopKm = 33.7` 而非實際一圈 34.5，
回繞點提前 0.8km → **有楽町 直接疊在 東京 上面**。

修正：`CLOSE_LOOP` 在段尾補回起站（東京 @ 34.5），使 東京 同時出現在 0.0 與 34.5
（與台鐵八堵同理，站 id 相同故前端 `lookupY` 會給它兩個 y）。驗證：
`loopKm=34.5`、東京 `km=[0, 34.5]`、`Y=[0, 518]`（34.5×scaleY 15.0 = 517.5）。

> 新增其他環狀視圖時務必檢查這點：**維基的環狀線表格幾乎都缺收尾那一段**。

### 站名正規化（`station_name.py`，三支腳本共用）

必須三邊共用同一套規則，否則維基與官方站名對不上、該站停靠整批被丟。
- 以「駅」切斷：維基站名後緊接記號（`東京駅山区`→東京、`川崎駅浜`→川崎、`塩尻駅◇`→塩尻）。
- **異體字轉換**：官方時刻表用舊字體「文挾」，維基用新字體「文挟」，NFKC 不會轉換，
  曾造成日光線該站 40 班車全部落空 → `KANJI_VARIANTS` 處理。

### 派段（`convert_timetable.py::assign_segments`）

走訪相鄰停靠對，取兩站共同所屬 segment，並貪婪讓同一 segment 延伸到不能再延伸。
跨線直通車（湘南新宿ライン 走 東海道→山手貨物→東北）會自然被切成數個 segment，
且不會像「對每個 segment 取站名交集」那樣在並行複線上重複輸出同一班車。

排序鍵最後一項是 **segment id**，用來保證決定性：`common` 是 set，迭代順序受字串
hash 隨機化影響，少了它平手時的選擇每次執行都不同（曾造成某些 segment 有無列車忽上忽下）。

### 派段斷點與連絡線（最容易出錯的地方）

**前端會自行補出兩個相鄰停靠之間的實體路徑**（沿拓樸找路）。因此若兩站在資料裡相鄰、
卻**沒有任何共同 segment**，引擎就會自己找一條路——而它找到的可能是繞錯邊的那條，
**連真正的停靠站都會被丟掉**。

實例（湘南新宿ライン 快速 2860Y 国府津→前橋）：`武蔵小杉` 與 `大崎` 原本沒有共同
segment，引擎便沿共用站把它繞成 `品川→東京→上野→池袋`，把實際停靠的
`大崎/恵比寿/渋谷/新宿` 整批丟掉（面板只剩 37 站，實際應為 41 站）。

因此 `convert_timetable.py` 內建 **`find_gaps()` 斷點偵測**，每次轉換都會列出
「兩站都在拓樸內但無共同 segment」的組合。已據此補上的連絡線：

| 連絡段 | 用途 | 沒有它會怎樣 |
|--------|------|--------------|
| `osaki_hinkaku_branch`（大崎–西大井）＋ `hinkaku_line` | 湘南新宿ライン・埼京線・相鉄直通 | 繞經 品川→東京→上野 |
| `keiyo_branch_futamata`（西船橋–南船橋）| 武蔵野線↔京葉線 | 繞經 総武線→千葉→蘇我 |
| `keiyo_branch_koya`（西船橋–市川塩浜）| 武蔵野線↔京葉線 | 同上 |
| `senseki_tohoku_conn`（塩釜–松島–高城町）| 仙石東北ライン | 繞經 仙台 大迴圈 |

### 通過站內插（`tools/interpolate_passes.py`）

轉換最後一步沿拓樸補出每對相鄰停靠之間的通過站（`v=2`，約 7.8 萬個，時刻表各 +1.8MB），
路徑從此由資料決定、不再交給前端猜。實例：NEX 2235M 新宿→渋谷→東京 原本在山手線視圖被畫成
渋谷→新宿→池袋→上野→東京（前端以 findIndex 取到 段頭 的東京），補完後正確走 大崎→品川→東京。

找路時暴露並已修正的拓樸問題：
- **`musashino_line_4` 假邊**：維基把 北小金支線／馬橋支線 攤平成 南流山–北小金–馬橋 一條鏈，
  常磐線列車抄了「北小金–馬橋 0.8km」→ 拆成 `musashino_branch_kitakogane` / `_mabashi`。
- **大崎支線營業キロ**：大崎–西大井 5.6km 是經品川的運費里程，渋谷→武蔵小杉 直達車被繞成
  大崎→品川→品鶴線 → `KM_OVERRIDE` 改成實際約 3.4km（近似值；本段無 preset 引用，不影響座標）。
- **已知限制**：藤沢↔大崎 直達（約 5 班）實際走品鶴線，但品鶴線經由（約 24.8km）物理上比
  東海道本線經品川（24.0km）長，最短路會選後者。影響僅限這幾班在東海道視圖的中間通過站。

轉換輸出的「派段斷點」清單現在附上實際採用的路徑，核對它是否符合實際走法即可。

**首尾斷點站也交給內插**：派段時與相鄰停靠沒有共同 segment 的首尾站（むさしの号 北朝霞→大宮
的 大宮）原本直接被丟掉；現在以單點段交給 PassInterpolator，找得到合理路徑就接上
（むさしの号 經 `musashino_line_3` 西浦和→与野→大宮）。隱含速度 >200km/h 者放棄
（花輪線 盛岡→大更、飯山線 長野→替佐：實際經 IGR／しなの鉄道，拓樸內只剩繞遠路）。

**前端配合**（`main.js`，通用、非特判）：
- `interpolatePassingStations()`：segment 若已完整（每對相鄰站在拓樸上都相鄰）就不再補站。
- `optimizeTrainTimesForDisplay()`：「0 分鐘行車 +0.5」與「停靠站撐開 +0.5」只作用在停靠站，
  通過站依原始時間比例重新對應到調整後的區間。否則 1314S 新川崎(891 停→891.5 發)後的
  川崎通過(891.25)會落在發車之前，線條折返。

> **剩下的斷點（約 54 種）是良性的**：多為特急長距離無停車區間（東京↔千葉 的しおさい、
> 八王子↔大月 的あずさ、上野↔柏 的ひたち…）。這些兩站雖無共同 segment，但引擎補的
> 路徑會經過正確的交會站（如 東京→錦糸町→千葉、八王子→高尾→大月），結果是對的。
> **判準：補出的路徑是否與實際走法一致**——不一致才要補連絡段。

### 列車配對：直通 vs 併結分離

官方詳情頁一頁可含多欄（多個列車番号），`convert_timetable.py` 依兩種規則配對：

1. **`action: "direct"`（直通）**：某站儲存格印有「直通」→ 與下一欄無縫接續。
   例：相鉄直通 特急 3120 → 普通 120M。（實測 2,367 組）
2. **`action: "split"`（併結／分離）**：同一頁、**同一列車名**的兩欄，是同一實體列車
   在某站分割的兩個編成；頁面**沒有**「直通」標記，故以「共同停靠站且發車時刻
   相差 ≤15 分」推斷交會站。（實測 36 組）

第 2 條是必要的，否則分割後的那一段看起來像「憑空從中途站發車」。實例：
**成田エクスプレス 50号** 為 12 輛編成，在 **東京** 分割成大船行與新宿行：

| 欄 | 車次 | 區間 |
|----|------|------|
| col=0 | `2050M` | 成田空港 19:49 → 空港第2ビル → 千葉 → 東京 20:51/20:53 → 品川 → 横浜 → 大船 |
| col=1 | `2250M` | 東京 20:56 → 渋谷 → 新宿 |

沒有配對時 `2250M` 的面板只顯示「東京 → 渋谷 → 新宿」，看不出它來自成田空港。
補上 `split` 後前端會串成 `成田空港 ▶ 新宿`，並在東京標注
`20:51/20:53(大船)/20:56(新宿)`。

> `空港第2ビル ↔ 東京` 會出現在派段斷點清單中（NEX 此區間不停車），屬**良性**
> ——引擎補的路徑經 千葉/錦糸町，與實際走法一致。

### 列車番号撞號（`uniquify_train_no`）

JR 東日本的列車番号只在各支社內唯一：全系統有約 4,200 個號碼被多班車共用（441M 就有
福島→米沢、大月→長野、長岡→新潟…共 7 班）。前端以 `no` 為主鍵（選取、直通配對、搜尋），
撞號時會出現「畫面亮 A 車、面板顯示 B 車」。依引擎既有慣例（JR_West 同法）撞號者改為
`號碼|首站id`（仍撞再加 `_首站發車分`），前端只顯示 `|` 之前。`coupled_with` 的 `train_id`
在改名後回填；對象整班跑在他社線而未輸出的配對直接移除（留著舊號碼會誤配到另一班同號車）。

### 同名跨運營商的站 (`AMBIGUOUS`)

りんかい線也有「大井町」，與 JR 京浜東北線的大井町是不同站。埼京線直通りんかい線的
車若把它當成 JR 大井町，就會與 `大崎` 形成假斷點（曾佔 304 筆）。`resolve_ambiguous()`
以「前後 2 站是否出現該他社專屬站」判斷，命中就標記 `_other_op`，使其不參與派段、
改歸入 `is_other` 段。

目前收錄：大井町（りんかい線）、青山（IGR；≠ 越後線 青山）、大和（相鉄；≠ 水戸線 大和）、
村上（東葉高速；≠ 羽越本線 村上）。青山 未處理前，花輪線直通 IGR 的車會把 盛岡↔青山
當成本系統相鄰停靠，前端沿拓樸從盛岡繞到新潟。

**找新的同名他社站**：掃 raw 中「本系統站、但前後鄰站都不在拓樸內」的停靠
（真正的交接站如 西日暮里↔千代田線 也會出現，逐一判斷是否為不同實體站）。

### 本系統內的同名異站 (`build_topology.py::HOMONYMS`)

站 id 以站名全域共用（交會站靠共用 id 偵測分岔），但 JR 東日本自己就有同名異站：

| 站名 | 另立 id 的一方 | 與其同名 |
|------|----------------|----------|
| 大久保 | 奥羽本線（秋田） | 中央線（東京） |
| 大沢 | 奥羽本線（山形線 米沢市） | 上越線（新潟） |
| 根岸 | 只見線（福島） | 根岸線（横浜） |

未拆開時，根岸線的列車會在只見線視圖的「根岸」列畫出一整排停靠點。`HOMONYMS` 以
`(prefix, 站名)` 另編 id（顯示名不變）；因此 `convert_timetable.py` 派段後輸出 `s`
一律用**該 segment 內**的站名→id（`seg_name2id`），全域 `name2id` 只用於「是否本系統站」
判斷與境界站/配對站後備（先出現者優先）。

**找新的同名異站**：列出「在多個 segment 出現、但在任何一段都不是端點」的 id，
排除並行複線（京浜東北∪東北本線 等）後剩下的就是可疑者。

### 他社直通 (`is_other`)

直通進入相鉄・東京メトロ（常磐緩行→千代田線、中央総武緩行→東西線）・小田急・
りんかい線・仙台空港鉄道・伊豆急行・東武・富士急・IGR・青い森・えちごトキめき 等
路網的區間，包成 `is_other: true` 的 segment（含 `system_name`）。前端不畫在運行圖，
而是在底部資訊面板以該 operator 名列出。段頭尾的**境界站用本系統拓樸 id**，
段內他社站用站名字串。validator 會對這些段/站出 WARNING，屬正常。

**完全跑在他社線上的班次**（相鉄 6228、小田急 6016、東京メトロ東西線 971S、
IGR 3419M、えちごトキめき 2362M 等，共約 1,161 班）在派段時找不到任何本系統
segment，**直接丟棄**——它們不是 JR 東日本的列車，只是因直通而出現在 JR 車站頁上。

### `time_stretch_ratio` 依視圖長度推導

LINEAR 視圖的 `scaleY = 畫面高 / 總km`，引擎令 `scaleX = scaleY * ratio`，因此
**列車線斜率 ∝ 速度(km/分) / ratio**、**畫面可見時間 ∝ 總km / ratio**。
`build_setting.py` 取 `clamp(總km / 120, 0.35, 1.0)`：短線（山手線 0.35）仍可看到約 3 小時；
上限 1.0 ≈ 在來線典型速度 1 km/分，讓長線的斜率接近 45°。舊版上限 3.0 時，中央線
（222km → 1.85）只看得到 3 小時，普通車被拉成近乎水平的線。

### 普通車細分運行系統（`SYSTEM_LABEL`）

東京圈的「普通」由多個運行系統共用車站（山手線視圖同時有山手線・京浜東北線・東海道線・
宇都宮/高崎線…），種別都叫「普通」無法區分。`convert_timetable.py` 把這類普通車的 `type`
換成所屬系統名，前端的車種篩選「普通」群組下就會出現 山手線／京浜東北線／… 可單獨開關，
顏色沿用該系統 preset 的 `button_color`。**系統色不可與種別色相近**：常磐線曾用青綠
`#20B2AA`，與「快速」`#5BD1C4` 撞色，取手–土浦 每日百餘班站站停普通被看成快速 → 改綠；
湘南新宿ライン 避開成田エクスプレス的粉紅（同在山手線視圖）→ 改紫。

**只在需要時標註**（`needs_system_label`）：同一段路上所有普通都站站停時（中央本線 大月–長野、
篠ノ井線），標「中央線」沒有資訊量，維持「普通」。以 (站, segment) 為單位，M = 同段上
「有相當份量的普通停、也有相當份量的普通通過」的站（兩者各 ≥10 班且 ≥ 對方的 10%，濾掉
武蔵野線 西浦和 這種只有少數むさしの号通過的例外）。普通車若停靠或通過了 M 中的站，或其相鄰
停靠區間與另一班「中間跳過 M 站」的車相同（高崎線 東京–上野 走自己的 segment、資料上
沒有通過站），才標註。

系統名的判定（`classify_system`）順序：

1. 包含該車**全部**停靠站的系統 preset 中，取總長最短者（山手線的車同時被 山手線 34.5km 與
   埼京線 大崎–池袋 包含 → 山手線）。
2. 走 東北本線別線 → 埼京線；走 大崎支線／赤羽線 → 湘南新宿ライン。
3. 覆蓋率 ≥60% 者中最高的（頭尾稍微超出的直通車：横浜線 橋本→桜木町、常磐線 土浦→品川）。

判定不了的（地方線普通車）維持「普通」。系統對照表在 `build_setting.py::SYSTEM_LABEL`，
為此新增了兩類 preset：`ueno_tokyo_utsunomiya`／`ueno_tokyo_takasaki`（上野東京ライン
熱海–宇都宮／高崎：東海道線與宇都宮・高崎線合併顯示）、`chuo_sobu_local`（中央・総武線各駅停車
三鷹–千葉；少了它，緩行線的車不會被任何單一系統完整包含）、`joban_local`（常磐線各駅停車
綾瀬–取手；與上野發著的中距離普通停站不同，須分開）。
「東海道線 (東京-熱海)」已被上野東京ライン兩個視圖完整涵蓋，不再列在路線選單；但仍以
`SYSTEM_ONLY_PRESETS` 保留作判定用，使東京發著、不直通的東海道線普通車判成「東海道線」。

### `train_color` 由實際資料生成

`build_setting.py` 讀已轉換的時刻表蒐集**實際出現的所有種別標籤**，確保每個都有顏色
（validator 會對缺色種別出 WARNING）。通用種別（普通/快速/特急…）套 skill 的日本線
統一色票；具名列車做成「種別＋愛称」（`特急ひたち`、`快速アーバン`，与 JR_West 命名
一致），号數去掉以免每個号數各自一色。`NAMED` 未收錄者依 `FALLBACK` 色池自動配色
（多為臨時/観光列車，如「快速ポケモントレイン気仙沼号」）。
